# TMD 打包与发布指南

> 版本：2.1　作者：chiangyang　更新：2026-11-21
> 适用平台：macOS（开发机）。Windows 安装包需在 Windows 上打包或用 CI，见 §7.2。
> 相关文档：[git-multi-remote.md](git-multi-remote.md)（双远程同步）
>
> **⚠ Electron 线状态（2026-11-14）**：Electron 架构已全面下线——壳层源码
> 已删除（git 历史可查），CI 不再构建 Electron 包，electron-builder 时代的
> 打包与故障记录也已随本文档 2.1 清理（git 历史可查）。最后版本 **0.1.8**
> （随 v0.2.1 发布）。0.1.x 老用户的更新/迁移链路分两部分维持：仓库
> `releases/latest*.yml`（0.1.8，指向 v0.2.1 的 Electron 附件）保持冻结，
> `migration.json` 随发版指向最新 Rust 安装包；配额清理以
> `MIGRATION_KEEP_TAG: v0.2.1` 锚点保护其指向的 Gitee 附件。0.1.x 用户
> 清零后删除 CI 的「Make migration.json」步骤、锚点 env 与冻结元数据
> 续传步骤即可彻底收尾。现行打包发布见 §1–§8，存量老用户迁移机制见 §9。

## 1. 打包命令速查

| 命令 | 产物 | 用途 |
|------|------|------|
| `npm run build` | `dist/`（网页产物） | 类型检查与生产构建，不打应用包 |
| `npm run dist:tauri:dir` | `src-tauri/target/release/bundle/macos/TMD.app` | macOS 只出应用包，不出 dmg |
| `npm run dist:tauri` | `src-tauri/target/release/bundle/` 下 .app + dmg（Windows 为 NSIS） | 本机完整打包，不生成 updater 签名 |
| `npm run dist:tauri:install` | 同 `dist:tauri:dir` + 覆盖安装到 `/Applications/TMD.app` | 本机安装验证 |
| `npm run dist:tauri:mac:signed` | dmg + `TMD.app.tar.gz` + `.sig` | macOS 发布构建，需要 updater 私钥 |
| `npm run dist:tauri:win:signed` | NSIS 安装包 + `.sig` | Windows 发布构建，需要 updater 私钥 |

产物目录为 `src-tauri/target/`（已在 `.gitignore` 中）。正式发布由 CI 在
macOS / Windows 双平台分别执行签名构建；macOS 安装包仍未做 Apple 公证，
首次从网页下载安装后的放行方式见 `docs/mac安装后启动报错解决方案.md`。

## 2. 日常更新流程（自己机器）

```bash
# 1. 确认改动可用
npm run build

# 2. 打包并覆盖安装（一条命令）
npm run dist:tauri:install

# 3. 启动与 release 页面冒烟
open -a TMD
npm run smoke:mac
```

**关键提醒**：文件关联（Finder 双击 .md 用 TMD 打开）绑定的是
`/Applications/TMD.app`。只跑 `dist:tauri:dir` 不覆盖安装的话，
双击 .md 打开的仍是已安装的旧版。

## 3. 正式发布（CI 双平台打包，自动发布 GitHub + Gitee）

日常自用更新见 [§2](#2-日常更新流程自己机器)，这里只讲正式发布流程。
GitHub Actions 在 macOS / Windows 上分别完成 Tauri 签名构建，再由 publish
job 发布 GitHub Release、生成 updater 元数据并上传 Gitee；失败/超时时用
本地通道补发（[§6](#6-gitee-发布ci-自动--本地快速通道)）。

### 前置条件（首次发布必做）

> GitHub 仓库 → `Settings → Secrets and variables → Actions → New repository secret`
>
> | Secret | 值来源 | 用途 |
> |--------|--------|------|
> | `TAURI_SIGNING_PRIVATE_KEY` | `npm run tauri signer generate` 生成的私钥内容 | 为双平台 updater 产物签名；必须与 `tauri.conf.json` 公钥配对 |
> | `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | 私钥密码（无密码则不设） | 签名密码 |
> | `GITEE_TOKEN` | Gitee → 设置 → 私人令牌 | 创建 Gitee Release、推元数据并上传附件，需 `projects` 等仓库权限 |

`GITHUB_TOKEN` 由 GitHub Actions 自动提供。任一必需 Secret 缺失都应让发布
失败，不能跳过签名或附件校验后继续发版。

### 发布步骤

以下位置的版本必须一致：
- `package.json` 与 `package-lock.json`
- `src-tauri/Cargo.toml` 与 `src-tauri/Cargo.lock`
- `src-tauri/tauri.conf.json`
- `CHANGELOG.md`：保留空 `[Unreleased]`，把本次内容转为 `[x.y.z] - 日期`；
  `node scripts/extract-release-notes.mjs --strict` 必须能提取当前版本小节
- `docs/需求说明.md` 的当前版本完成记录
- git tag：`v` + version

```bash
# 1. 提交版本、更新日志与发布链改动
git add -A && git commit -m "chore(release): prepare v0.2.2"

# 2. 先推代码并等待日常 CI（前端 + macOS/Windows Rust）通过
git push gitee master
git push github master:main

# 3. 在同一提交上打正式 tag，并分别显式推送
git tag v0.2.2
git push gitee v0.2.2
git push github v0.2.2

# 4. GitHub tag 触发 Release：双平台签名构建 → 产物完整性校验 →
#    GitHub Release → Gitee Release 与 releases/ 元数据提交
# 5. Gitee 元数据提交合回本地后再同步双端
git pull gitee master --no-rebase
git push github master:main
```

> **提示**：本项目没有 `origin` 远程，只有 `gitee` 和 `github` 两个。
> 本地分支是 `master`，GitHub 远程分支是 `main`，所以推 GitHub 时需要
> `master:main` 映射。详见 [git-multi-remote.md](git-multi-remote.md)。

### 版本与标签保护

Release 工作流会从 `package.json` 推导唯一发布标签 `v<version>`：tag 触发时
若与 `tauri.conf.json` 或推送标签不一致立即失败；手动触发也只使用该版本标签，
不会把 `main` 分支名当成 Release。发布前还会强制检查 macOS / Windows 安装包、
updater 包与签名文件，任一缺失即停止。正式发版使用匹配版本的 tag，不再用
`vX.Y.Z-test` 测试标签绕过校验。CI workflow 见 [§4](#4-ci-发布工作流)。

### 热修复版本号（-Fix-N）

发完某个版本后若发现 bug，可在**同一 base** 上叠 `-Fix-N` 热修复，而不必
每次都 bump patch：

```
0.2.4  →  0.2.4-Fix-1  →  0.2.4-Fix-2  →  0.2.4-Fix-3  ……
```

- **能被自动更新识别**：`src-tauri/src/updater.rs` 的 `tmd_is_update` 注册为
  updater 插件的自定义版本比较器（`bootstrap/mod.rs`），定义同一 base 下
  `Fix-N` 比正式版新、且按数字 N 递增（`Fix-10 > Fix-2`，非字典序）。其余
  预发布（`-beta` / `-rc`）仍走标准 semver，不会误推给正式版用户。
- **发布链路透明透传**：版本号是字符串，CI 的 tag 触发（`v*`）、版本一致性
  校验、产物命名（`TMD_0.2.4-Fix-1_x64-setup.exe` /
  `TMD_0.2.4-Fix-1_aarch64.dmg`）、`latest.json` 的 version / url、macOS
  `CFBundleShortVersionString` 全部正常（已实测 debug 构建通过）。
- **版本一致性约束不变**：发 `-Fix-N` 时仍需四处同步——`package.json` /
  `package-lock.json`、`Cargo.toml` / `Cargo.lock`、`tauri.conf.json`、
  `CHANGELOG.md` 新增 `[0.2.4-Fix-1]` 小节，tag 打 `v0.2.4-Fix-1`。
- ⚠️ **首个热修必须 bump patch**：自动更新的比较逻辑烧在客户端二进制里，
  **已经发出去的旧版本不认识 `-Fix-*`**（其内置的是默认 semver，而
  `0.2.4-Fix-1 < 0.2.4`，会被判为不是更新）。因此从一个不含自定义比较器的
  版本跨过来时，第一次热修要发成更高的 patch 让旧用户能拉到；装上带比较器的
  版本之后，后续的 `-Fix-N` 才能被自动识别并递进。`0.2.4` 起已内置比较器，
  故 `0.2.4` 之后的热修可直接叠 `-Fix-N`（如 `0.2.4-Fix-1`），无需再 bump patch。

## 4. CI 发布工作流

配置文件：`.github/workflows/release.yml`，push tag `v*` 自动触发。

### 4.1 工作流设计

两个 job（构建与发布分离）：

| Job | 平台 | 职责 |
|-----|------|------|
| `build-tauri` | macos-latest + windows-latest（并行） | 校验 npm / Tauri 配置 / tag 版本；执行签名构建；macOS 运行观察性 GUI 冒烟；收集并上传双平台 artifact |
| `publish` | ubuntu-latest（依赖 build-tauri 成功） | 再次校验版本与必需产物，提取更新日志，生成 `latest.json` / `migration.json`，发布 GitHub + Gitee Release，并推送 Gitee raw 元数据 |

发布前强制检查以下 Tauri 产物均存在且非空，缺任一项即停止：

- `TMD_<version>_x64-setup.exe` 与 `.sig`
- `TMD_<version>_aarch64.dmg`
- `TMD.app.tar.gz` 与 `.sig`

macOS 的 dmg 只用于首次安装和 Electron 老用户手动迁移；应用内更新使用
`TMD.app.tar.gz`，其签名对应 updater 包而不是 dmg。Windows 使用签名 NSIS
安装包更新。纯 Tauri 发版不再生成或上传 Electron blockmap、zip、ULMO dmg。

**GitHub Release 直接发布、不用草稿**：GitHub updater 端点是
`releases/latest/download/latest.json`，草稿对该端点不可见；版本、签名产物和
更新说明已在同一 workflow 内校验，无需人工二次把关。

### 4.2 Gitee 跨国链路的实测约束（决策记录）

Gitee 的 CI 自动上传**保留但很慢**，实测四条硬约束（本地快速通道见 §6）：

1. **跨国链路太慢**：GitHub Actions runner 在海外，历史 Electron 大包实测把
   170MB 附件传到 Gitee 需要 1 小时以上（本地网络仅分钟级）——一条
   `git clone` 都要数分钟；当前 Tauri 包更小，但仍保留超时与本地补发通道
2. **contents API 有反爬拦截**：Gitee 对海外 IP 的 contents API 写操作持续
   返回 405（POST 需把 path 放进 URL，PUT 另有拦截），元数据根本写不进去
3. **CI 直推 master 造成仓库分叉**：CI 推一个元数据提交后，Gitee master 领先
   本地，下次 `pushall` 会被拒（non-fast-forward），需先
   `git pull gitee master --no-rebase` 合并
4. **runner 单 job 上限 6 小时**：GitHub-hosted runner 的平台硬限制，
   `timeout-minutes` 设再大也会被掐断——job 取满 6 小时（360 分钟）、
   Gitee 步骤 355 分钟（超时由步骤先行报错，错误信息可见）。实测 3.7 小时
   的传输在限内，但余量有限，故保留本地快速通道作为兜底

### 4.3 需要配置的 Secret

> ⚠️ 这是 CI 发布的**前置条件**，首次发布前必须配好。详见 [§3 前置条件](#3-正式发布ci-双平台打包自动发布-github--gitee)。

| 仓库 | Secret | 用途 |
|------|--------|------|
| GitHub | `GITHUB_TOKEN`（自动提供） | 写 GitHub Release |
| GitHub | `TAURI_SIGNING_PRIVATE_KEY` | 双平台 updater 产物签名，缺失时构建失败 |
| GitHub | `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`（可选） | 私钥密码；无密码则不设 |
| GitHub | `GITEE_TOKEN` | 创建 Gitee Release、推元数据并上传附件，缺失时 Gitee 步骤失败 |

GitHub Release 先于 Gitee 发布；若 Gitee Secret 或跨国链路失败，保留已完成的
GitHub Release，修复原因后用 §6 本地通道补发，不重打 tag、不绕过签名校验。

### 4.4 手动触发

GitHub Actions 页面可用 `workflow_dispatch` 手动触发完整的双平台构建与发布。
手动触发同样从 `package.json` 推导 `v<version>`，并校验 `tauri.conf.json`，
不会把 `main` 分支名当成 Release tag，也不能用来发布任意历史版本。重跑时
GitHub 会复用 Release 并覆盖同名附件，Gitee 会复用已有 Release；代码或版本
已变化时应走正式 tag，不用手动触发替代版本管理。

## 5. 日常 CI（ci.yml）

配置文件：`.github/workflows/ci.yml`（2026-09-18 新增）。与 §4 的发布工作流互补：
release.yml 保证「打 tag 时产物可构建」，ci.yml 保证「主干随时可用」。

- **触发**：push 到 `master` / `main`（即每次 `git pushall`）、提交 PR、手动触发；
  同分支连续 push 自动取消旧任务（concurrency）
- **前端 check（Ubuntu）**：`npm run lint` → `npx tsc --noEmit` → `npm test`
  → `npx vite build`
- **Rust 编译门禁（macOS + Windows）**：分别执行 `cargo fmt --check` 与
  `cargo test`，覆盖 `cfg(target_os)` 平台分支；前端 `dist/` 用占位文件满足
  Tauri 编译期 codegen，完整前端构建由 check job 负责
- **边界**：macOS release 应用的真实窗口冒烟用 `npm run smoke:mac` 在本地执行；
  Release 工作流也运行该检查，但目前保留 `continue-on-error` 观察 CI GUI 会话。
  Windows 的安装与更新仍需 Windows 环境实测，不能由编译成功替代
- **权限**：`contents: read`——只读令牌，结构上不可能碰 tag / Release / 发布

### 本地提交门禁（pre-commit hook）

仓库内 `.githooks/pre-commit` 在提交前执行与 CI 对齐的轻量检查：
有 `src-tauri/**/*.rs` 改动跑 `cargo fmt --check`（rust job 的格式步骤），
有前端/脚本改动跑 `tsc --noEmit`（check job 的类型检查）。

**启用自动完成**：`package.json` 的 `prepare` 生命周期脚本（`git config
core.hooksPath .githooks`）在 `npm install` / `npm ci` 后自动执行——克隆
后照常安装依赖即可，无需手动配置。`core.hooksPath` 是 git 本地配置，
无法随仓库分发（git 不自动执行仓库内脚本的安全设计），故挂在安装步骤上。

- 未装依赖就想提交：手动 `git config core.hooksPath .githooks`（一次）
- 跳过检查：`git commit --no-verify`
- 无 `.git`（zip 下载）时 prepare 静默跳过（`|| true`）

背景：v0.2.0 后首个提交因 rustfmt 缩进不符导致 CI 双平台 rust job 红
（编译本身通过，本地不易察觉）。

## 6. Gitee 发布：CI 自动 + 本地快速通道

Gitee 有两条通路，按情况选：

| 通路 | 耗时 | 适用 |
|------|------|------|
| **CI 自动**（publish job 的 Upload to Gitee） | 实测 3.7 小时 | 默认，无需人工干预；受 runner 单 job 6 小时硬上限约束（见 §4.2） |
| **本地快速通道**（`npm run release:gitee`） | 分钟级 | CI 超时/失败后补发，或想立刻发完 |

两条通路使用同一版本化元数据：`latest.json` 必须包含 Windows / macOS 的下载
地址与非空签名，`migration.json` 指向同版本 Rust 安装包；冻结的 Electron
`latest*.yml` 不由本地补发脚本改写。

> **CI 自动通路的分叉处理**：CI 会往 Gitee master 推一个元数据提交，导致
> Gitee master 领先本地。下次 `pushall` 前执行一次
> `git pull gitee master --no-rebase`（产生一个 merge 提交）即可继续正常推送。

### 6.1 前置

Gitee 仓库需已有与 GitHub 同名的正式 tag，按 §3 分别显式推送。CI 自动通路
还需在 GitHub 仓库 Secrets 配置 `GITEE_TOKEN`；本地脚本读取公开 GitHub
Release 不需要 GitHub token，Gitee Release 与附件通过网页手动处理。

### 6.2 本地快速通道步骤

```bash
# 1. 确认 GitHub Release 已发布（非草稿），且当前 tag 的 Tauri 产物齐全

# 2. 校验并写入 releases/latest.json 与 releases/migration.json
#    优先采用 Gitee raw 的当前完整副本，否则回退 GitHub Release 附件；
#    不会改写冻结的 latest.yml / latest-mac.yml
npm run release:gitee

# 3. 按脚本输出的清单，从 GitHub Release 下载并上传 6 个文件到同 tag 的
#    Gitee Release：dmg、exe、app.tar.gz、两个 .sig、latest.json

# 4. 提交元数据并同步双端
git add releases/ && git commit -m "chore: update release metadata for vX.Y.Z"
git push gitee master
git push github master:main
```

> **为什么元数据必须来自本次 Release**：签名与下载地址必须和 CI 实际发布的
> 产物匹配，不能用普通本地构建另算一份。脚本会拒绝旧版本 JSON，以及缺少
> Tauri 双平台条目、下载地址或签名的 `latest.json`。
>
> `node scripts/prepare-gitee-release.mjs --local` 仅用于 `release/` 已准备好
> 当前 CI 元数据的特殊补发场景，不是常规本地打包后的替代流程。

> **为什么 URL 指向 Release 附件**：Tauri updater 从 raw 端点读取
> `latest.json`，再直接使用其中各平台的绝对下载 URL。安装包在 Release 附件区，
> 不在 `raw/master/releases/` 目录；`migration.json` 的下载地址同理。

### 6.3 平台差异（自动更新）

| 平台 | 自动更新 | 说明 |
|------|----------|------|
| Windows | ✅ 全自动 | tauri-plugin-updater 下载带 minisign 签名的 NSIS 安装包，保存未修改文档后安装并重启 |
| macOS | ✅ 全自动 | 下载并校验 `TMD.app.tar.gz` 后原地替换应用；dmg 只用于首次安装与 Electron 老用户手动迁移 |

双平台均按 `tauri.conf.json` 的 endpoints 顺序尝试 Gitee、GitHub，更新为全量
下载，不使用 Electron 时代的 blockmap 差量索引。

### 6.4 Gitee 附件配额（1GB）与自动清理

Gitee 免费仓库的 **Release 附件总容量为 1GB**。当前纯 Tauri 每版上传 dmg、
exe、updater 包、签名与 `latest.json`，约 15MB；历史 Electron 版本体积更大，
v0.1.5 曾实测累计 1036MB 后上传被配额拒绝。

CI 在「Upload to Gitee」上传前自动做配额维护（工作流内常量
`KEEP_GITEE_RELEASES`，默认 2）：按创建时间保留最近 2 个版本的附件，更早
版本的附件逐个删除——**Release 页面与更新说明保留，旧安装包仍可从 GitHub
Release 下载**；当前发版的 Release ID 和 `MIGRATION_KEEP_TAG: v0.2.1` 锚点
始终排除在清理之外，清理失败只告警、不阻断发版。锚点保护的是 Electron 0.1.8
老用户更新 / 迁移链所依赖的附件，不能当作普通旧版本删除。

本地快速通道（§6.2）补传前若遇配额错误，可手动清理：Gitee 仓库 →
Releases → 打开旧版本 → 删除附件（保留最近 1–2 个版本及 v0.2.1 锚点）。

## 7. Tauri 本地打包与安装

Electron 壳已下线，当前唯一桌面应用为 Rust + Tauri，正式应用名是 `TMD.app`，
identifier 为 `com.chiangyang.tmd`。迁移过程与历史评估存于 git 历史。

### 7.1 macOS

| 命令 | 产物 | 用途 |
|------|------|------|
| `npm run dist:tauri` | `src-tauri/target/release/bundle/` 下 .app + dmg | 本机完整打包，不生成 updater 签名 |
| `npm run dist:tauri:dir` | `.../bundle/macos/TMD.app` | 只出应用包不出 dmg（`--bundles app`） |
| `npm run dist:tauri:install` | 打包并覆盖安装到 `/Applications/TMD.app` | 本机安装与文件关联验证 |
| `npm run dist:tauri:mac:signed` | dmg + `TMD.app.tar.gz` + `.sig` | 发布构建，需要 updater 私钥 |

安装后运行 `open -a TMD` 与 `npm run smoke:mac`。只构建不覆盖安装时，Finder
双击 .md 仍可能打开 `/Applications/TMD.app` 中的旧版。

### 7.2 Windows（在 Windows 机器上跑）

| 命令 | 产物 | 用途 |
|------|------|------|
| `npm run dist:tauri:win` | `src-tauri/target/release/bundle/nsis/TMD_<版本>_x64-setup.exe` | 出 NSIS 安装包，不生成 updater 签名 |
| `npm run dist:tauri:win:dir` | `src-tauri/target/release/tmd.exe`（裸 exe，`--no-bundle`） | 只编译不打包，快速验证 release 编译 |
| `npm run dist:tauri:win:open` | 资源管理器打开安装包目录（不重新打包） | 打包后取产物 |
| `npm run dist:tauri:win:signed` | NSIS 安装包 + `.sig` | 发布构建，需要 updater 私钥 |

Windows 前置条件：Rust 工具链（rustup stable，**MSVC 目标**，需 VS 2022
Build Tools +「使用 C++ 的桌面开发」工作负载）与 `@tauri-apps/cli`；
WebView2 Runtime Win11 自带。裸 exe 可直接运行。NSIS 工具链由 tauri-cli
首次打包时自动下载（走 github.com，网络不通时挂代理重试，缓存于
`%LOCALAPPDATA%\tauri\`）。

### 7.3 构建边界

- `package.json`、`src-tauri/Cargo.toml` 与 `src-tauri/tauri.conf.json` 的版本
  必须一致，不再允许壳层版本独立漂移
- 普通 `dist:tauri*` 用于日常安装验证；正式更新包必须用 `*:signed` 命令或 CI
  签名构建，并同时保留安装包、updater 包与对应 `.sig`
- 产物目录为 `src-tauri/target/`（Cargo 惯例，已忽略）；release 优化配置在
  `src-tauri/Cargo.toml`，前端产物由 tauri-codegen 压缩后嵌入二进制
- 日常开发用 `npm run tauri dev`；只验证 Rust 改动可在 `src-tauri/` 下运行
  `cargo check` / `cargo test`

## 8. Tauri 自动更新（tauri-plugin-updater）

> 状态（2026-11-16）：**当前唯一桌面更新链**。`src-tauri/src/updater.rs` +
> shim 七条通道（检查/下载/安装/开关/状态订阅/保存握手×2）已接通；release.yml
> 只构建 Tauri 签名产物，publish job 生成并上传 `latest.json` 到 GitHub / Gitee
> 双 Release，同时更新 Gitee raw 副本。发版前必须确认
> `TAURI_SIGNING_PRIVATE_KEY` Secret 与 `tauri.conf.json` 公钥配对。

### 8.1 与 Electron 旧版的差异

| 维度 | Electron 0.1.8（历史实现） | Tauri（tauri-plugin-updater） |
|------|----------------------------|-------------------------------|
| 校验 | 自研 sha512（元数据同源，只防传输损坏） | minisign 签名（私钥离线持有，防篡改） |
| 下载量 | blockmap 差量 | **全量**（体积换简单） |
| 双源 | Gitee 主 + GitHub 备（失败切一次） | `plugins.updater.endpoints` 按序回退（同双源） |
| Windows 安装 | 下载 → 用户点「重启并安装」 | 下载完成即安装 → 保存握手 → 自动重启 |
| macOS 安装 | 自下 dmg + 引导手动拖入 | 插件负责（`TMD.app.tar.gz` 原地替换） |
| 元数据 | `releases/latest.yml`（electron-builder 格式） | `releases/latest.json`（Tauri 格式，见 11.3） |

### 8.2 签名密钥（已完成，2026-10-28）

已在本机生成（**无密码**密钥对，路径为本机用户目录，不在仓库内）：

| 文件 | 位置 | 用途 | 仓库状态 |
|------|------|------|----------|
| 私钥 | `~/.tauri/tmd-updater.key` | 打包时签名，产出 `.exe.sig` | ❌ 不进仓库；**须离线备份** |
| 公钥 | `~/.tauri/tmd-updater.key.pub` | 内置到应用里验签 | ✅ 已填 `tauri.conf.json` 的 `plugins.updater.pubkey` |

**重新生成**（会同时让已发布的旧版本无法接受新包，慎用）：

```bash
npm run tauri signer generate -- -w ~/.tauri/tmd-updater.key
```

**CI 需要两个 Secret**：`TAURI_SIGNING_PRIVATE_KEY`（私钥文件内容）、
`TAURI_SIGNING_PRIVATE_KEY_PASSWORD`（无密码时留空或不设）。前者是构建门禁，
缺失或公钥不匹配时不得继续发布无签名更新包。

**为什么签名开关不在基础配置里**：`bundle.createUpdaterArtifacts` 为 true 时
缺私钥会直接让构建失败，会打断日常 `npm run dist:tauri:win`。因此改为 opt-in：

| 命令 | 用途 | 产物 |
|------|------|------|
| `npm run dist:tauri:win` | 日常打包（不签名） | NSIS 安装包 |
| `npm run dist:tauri:win:signed` | **发版打包（带签名）** | 安装包 + `.sig` |
| `npm run dist:tauri:mac:signed` | macOS 发版打包 | dmg + `.app.tar.gz` + `.sig` |

签名构建脚本（`scripts/tauri-build-signed.mjs`）会叠加
`src-tauri/tauri.updater.conf.json`，并按
`$TAURI_SIGNING_PRIVATE_KEY` → `$TMD_UPDATER_KEY_PATH` →
`~/.tauri/tmd-updater.key` 的顺序找私钥。

更新产物只在签名构建叠加配置中开启。发布时必须核对 `.sig` 非空，并把其内容
写入 `latest.json` 对应平台的 `signature`；只上传安装包而没有有效签名，仍视为
发布失败。

### 8.3 latest.json 格式

两个端点读同内容（`plugins.updater.endpoints` 按序回退）：

```json
{
  "version": "0.2.2",
  "notes": "本次更新说明",
  "pub_date": "2026-11-16T00:00:00Z",
  "platforms": {
    "windows-x86_64": {
      "signature": "<安装包 .sig 文件内容>",
      "url": "https://gitee.com/chiangyangNPU/tmd/releases/download/v0.2.2/TMD_0.2.2_x64-setup.exe"
    },
    "darwin-aarch64": {
      "signature": "<app.tar.gz .sig 内容>",
      "url": "https://gitee.com/chiangyangNPU/tmd/releases/download/v0.2.2/TMD.app.tar.gz"
    }
  }
}
```

发布位置：Gitee `releases/latest.json`（分支须 `master`，CDN 缓存约 5 分钟，
与 §4.2 同约束）；GitHub 侧放 Release 资产，端点用
`releases/latest/download/latest.json`。

### 8.4 回归

- 发布产物：双平台安装包、updater 包与 `.sig` 均非空；`latest.json` 版本正确，
  两个平台的 URL 可下载、签名字段非空
- 双端点：Gitee raw 与 GitHub `releases/latest/download/latest.json` 返回同一版本；
  Gitee 主源不可用时能回退 GitHub
- 手动：设置面板「检查更新」→ 无新版提示 / 有则弹原生对话框（下载并安装 / 稍后）
- 自动：勾选「启动时自动检查更新」→ 重启后 5 秒触发（公钥未配时跳过，
  避免每次启动静默报错）
- 保存握手：更新重启前发 `tmd-doc-save-request`，渲染层保存后回
  `tmd-doc-save-result`（5 秒超时放行）——未保存内容不因更新丢失
- 实机升级：至少验证 macOS 上一正式版升级到当前版；Windows 若未做实机测试，
  发布记录只声明 CI 构建、签名与元数据校验，不宣称已验证真机更新

## 9. 架构迁移提示（Electron 老用户 → Rust 版）

> **现状（2026-11-14）**：Electron 壳已下线，本节机制仍对存量 0.1.x 用户
> 生效——migration.json 由 CI **无条件生成**（版本跟随 package.json，即最新
> Rust 版），0.1.8 用户手动检查更新时被引导到最新 Rust 安装包。0.1.x 用户
> 清零后删除 CI 的「Make migration.json」步骤 + `MIGRATION_KEEP_TAG` 锚点
> env + 冻结元数据续传步骤即可收尾。

Electron 用户只会收到 **0.1.x 维护线**更新（`latest.yml`，已冻结在 0.1.8）；
跨架构安装器体系不同（Squirrel/NSIS vs tauri-plugin-updater），**无法自动
升级到 0.2.x**。迁移提示解决「老用户不知道 Rust 版已就绪」——只能引导手动
下载安装一次。

### 产物与端点

- `scripts/make-migration-json.mjs` 生成 `migration.json`
  （`version` / `notes` / `downloads.darwin`(dmg) / `downloads.win32`(setup.exe)，
  下载地址为 Gitee Release 附件绝对地址）
- 发布：GitHub Release 附件 + `releases/migration.json`（Gitee raw 端点
  `https://gitee.com/chiangyangNPU/tmd/raw/master/releases/migration.json`；
  GitHub 备用 `releases/latest/download/migration.json`）
- Electron 0.1.8 内置逻辑（历史源码 `electron/updater.cjs`）：**仅手动检查更新**时
  先拉 migration.json——目标版本严格高于当前版本 → 原生对话框三选一：

  | 按钮 | 行为 |
  |------|------|
  | 下载 Rust 版 | **应用内下载**（Electron 下载栈，带进度）→ mac：dmg 落「下载」目录、清隔离标记、弹窗「关闭应用并打开安装包」引导拖入「应用程序」替换旧版；Windows：setup.exe 落临时目录，弹窗后运行安装器并退出应用 |
  | 稍后（Esc 同） | 记 `migrationPrompted`=目标版本；下次检查再问，新版本发布重新提示 |
  | 继续使用 0.1.x | 记 `migrationDeclined`=true（永久不再提示），**继续执行常规更新检查**——用户照常停留在 0.1.x 维护线 |

  对话框正文按平台说明安装后续动作（macOS：替换「应用程序」旧版、无需手动卸载；
  Windows：两代安装器独立，旧版**不会**自动移除，需在「设置 → 应用」手动卸载）。
  自动检查不提示（避免启动打扰）；拉取失败/超时一律静默，不影响常规更新

### 回归清单（迁移机制变更后验证一次）

1. `node scripts/make-migration-json.mjs --version X --mac-dmg …… --win-setup ……`
   本地生成，检查 URL 与版本
2. Electron 0.1.8 手动「检查更新」→ 弹迁移对话框 →「下载 Rust 版」应用内下载
   正确平台的最新 Tauri 安装包
3. 再次检查更新 → 不再弹（同版本只提示一次）；删除 shell-state.json 的
   `migrationPrompted` 可复测
4. 在测试更新源临时移除 migration.json → Electron 回退到常规 0.1.x 更新检查，
   拉取失败或超时不影响旧版使用；恢复文件后迁移提示仍可工作
