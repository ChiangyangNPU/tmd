# TMD 打包与发布指南

> 版本：1.4　作者：chiangyang　更新：2026-09-18
> 适用平台：macOS（开发机）。Windows 安装包需在 Windows 上打包或用 CI，见 §5。
> 相关文档：[git-multi-remote.md](git-multi-remote.md)（双远程同步）

## 1. 打包命令速查

| 命令 | 产物 | 用途 |
|------|------|------|
| `npm run build` | `dist/`（网页产物） | 只编译验证，不打应用包 |
| `npm run dist:dir` | `release/mac-arm64/TMD.app` | 日常自用的 Mac 应用（未压缩目录形式） |
| `npm run dist` | `release/TMD-x.x.x-arm64.dmg`（约 124MB） | 分发给别人的 Mac 安装镜像 |
| `npm run dist:install` | 同 dist:dir + 自动覆盖安装到 /Applications | **推荐日常使用**，一步到位 |

全部命令均**跳过 macOS 代码签名**（`build.mac.identity = null`）：
当前仅有的 Apple Development 证书不能用于分发公证，签名对自用与未公证分发
均无收益，却耗时 3-7 分钟。将来若购买 Developer ID 证书并配置公证，删除
该配置项即可恢复签名流程。

打包耗时约 **8 秒**（2026-09-06 优化后；此前因 macOS 代码签名耗时 3-7 分钟）。
产物目录 `release/` 已在 .gitignore 中，不会进仓库。

> 速度原理：编译仅约 4 秒，慢的是 electron-builder 默认的 macOS 代码签名
> （Apple Development 证书，对自用无收益且不能用于分发公证）。
> 已通过 `build.mac.identity = null` 跳过签名；
> **将来配置 Developer ID 证书与公证时**，删除该配置项即可恢复。

## 2. 日常发布流程（自己机器上更新）

```bash
# 1. 确认改动可用
npm run build

# 2. 打包并覆盖安装（一条命令）
npm run dist:install

# 3. 启动验证
open -a TMD
```

**关键提醒**：文件关联（Finder 双击 .md 用 TMD 打开）绑定的是
`/Applications/TMD.app`。只跑 `dist:dir` 不覆盖安装的话，
双击 .md 打开的永远是旧版。

## 3. 正式发布（触发 CI 自动打包 + 双源发布）

日常自用更新见 [§2](#2-日常发布流程自己机器上更新)，这里只讲正式发布流程。

### 前置条件（首次发布必做）

GitHub Actions CI 会自动打双平台包并发布到 GitHub + Gitee，但需要先在
**GitHub 仓库** 配置一个 Secret，否则 Gitee 上传 Job 会直接报错失败
（不会静默跳过——缺失 token 一律 `exit 1`，避免「CI 全绿但产物缺失」）：

> GitHub 仓库 → `Settings → Secrets and variables → Actions → New repository secret`
>
> | Secret | 值来源 | 权限 |
> |--------|--------|------|
> | `GITEE_TOKEN` | Gitee → 设置 → 私人令牌 | `projects`、`issues`、`pull_requests` |

CI 用的 `GITHUB_TOKEN` 由 GitHub Actions 自动提供，无需手动配置。

### 发布步骤

版本号三处保持一致：
- `package.json` 的 `version`
- `docs/需求说明.md` 里对应版本的完成状态
- git tag 名（`v` + version）

```bash
# 1. 改版本号（package.json + docs/需求说明.md）

# 2. 提交
git add -A && git commit -m "chore: bump to v1.0.0"

# 3. 打 tag
git tag v1.0.0

# 4. 推送到两个远程（都要推，推 GitHub 才会触发 CI）
git push gitee master --tags
git push github master:main --tags

# 一条命令也可以（先用 pushall 推代码，再单独推 tag）：
# git pushall && git push gitee master --tags && git push github master:main --tags

# 5. CI 自动：双平台并行打包 → GitHub Release → Gitee Release + raw 目录
```

> **提示**：本项目没有 `origin` 远程，只有 `gitee` 和 `github` 两个。
> 本地分支是 `master`，GitHub 远程分支是 `main`，所以推 GitHub 时需要
> `master:main` 映射。详见 [git-multi-remote.md](git-multi-remote.md)。

### 首次发布建议：先用测试 tag 验证

第一次用 CI 发布时，建议先打一个测试 tag 确认流程跑通，再发正式版：

```bash
git tag v0.1.1-test
git push gitee master --tags
git push github master:main --tags
```

到 GitHub Actions 页面（仓库 → Actions → Release）查看运行状态。
macOS + Windows 双平台并行打包，大约 5-10 分钟完成。成功后 GitHub Release
能看到 dmg + exe 安装包；**Gitee Release 只能拿到 exe**——dmg 超出 Gitee
附件单文件 100MB 上限会被服务端拒绝，`publish-gitee` 会因此报错（见
[§7.2](#72-gitee-上传逻辑)）。

验证完删除测试 tag：

```bash
git tag -d v0.1.1-test
git push gitee :refs/tags/v0.1.1-test
git push github :refs/tags/v0.1.1-test
# Gitee Release 可能需要在网页上手动删除
```

CI workflow 见 [§7](#7-ci-发布工作流)。

## 4. 签名与公证（macOS 分发给别人时）

当前状态：打包时 electron-builder 会自动用本机的 **Apple Development 证书**签名
（日志里 `signing ... identityName=Apple Development: ...`）。

| 分发范围 | 需要什么 | 现状 |
|----------|----------|------|
| 自己机器 | 无 | ✅ 可直接用 |
| 别人的 Mac | Developer ID 签名 + 公证（notarization） | ⚠️ 未配置 |

未公证的 app 发给别人时，对方首次打开需右键 → 打开（绕过 Gatekeeper），
或在系统设置 → 隐私与安全性里手动放行。要正式公证需要：

1. Apple Developer Program membership（$99/年，Development 证书不能公证）
2. 创建 **Developer ID Application** 证书
3. `package.json` → `build.mac` 增加 notarize 配置（Apple ID + App-specific password）

## 5. Windows 安装包

`build.win.target = nsis` 已配置。macOS 上打不出完整的 Windows 包，
需在 **Windows 机器**上打包（CI 的 windows-latest 也会打，见 [§7](#7-ci-发布工作流)）。

### 5.1 环境准备

1. 安装 [Node.js](https://nodejs.org/)（建议 LTS 版本）
2. Electron 国内镜像已在 `package.json` 的 `build.electronDownload.mirror` 中配置
   （`npmmirror`），Electron 二进制下载不卡

### 5.2 打包命令

| 命令 | 产物 | 用途 |
|------|------|------|
| `npm install` | —— | 首次安装依赖 |
| `npm run dist` | `release/TMD-x.x.x-x64-Setup.exe` | NSIS 安装程序，双击安装（含 .md/.markdown 文件关联） |
| `npm run dist:dir` | `release/win-unpacked/TMD.exe` | 免安装目录形式，直接运行其中的 exe |
| `npx electron-builder --win portable` | `release/TMD x.x.x.exe` | 单文件免安装绿色版（临时命令，不写入脚本） |

产物目录（`release/`）内容说明：

| 产物 | 说明 |
|------|------|
| `TMD-x.x.x-x64-Setup.exe` | 最终 NSIS 安装程序（分发用这个），命名由 `build.nsis.artifactName` 控制，与 mac 的 dmg 命名风格一致 |
| `TMD-x.x.x-x64-Setup.exe.blockmap` | 自动更新差量下载用的 blockmap（随 Release 上传，本地无用） |
| `win-unpacked/` | 未压缩的应用目录，其中的 `TMD.exe` 可直接运行（免安装形态） |
| `*.nsis.7z` 等中间文件 | NSIS 构建中间产物，打包完成后自动清理，无需理会 |

### 5.3 Windows 常见问题

- **NSIS / winCodeSign 工具链下载失败**：设置镜像后在项目目录重打（PowerShell）：

```powershell
$env:ELECTRON_BUILDER_BINARIES_MIRROR = 'https://npmmirror.com/mirrors/electron-builder-binaries/'
npm run dist
```

- **跨平台脚本说明**：`dist` / `dist:dir` 脚本不使用 Unix 风格的
  `CSC_IDENTITY_AUTO_DISCOVERY=false` 环境变量前缀（Windows cmd 无法识别，
  会报 `'CSC_IDENTITY_AUTO_DISCOVERY' is not recognized`），关闭 macOS 签名
  统一走 `build.mac.identity = null` 配置项，Windows / macOS 通用。
- **本地打包最后报 `GH_TOKEN is not set`**：CI 环境下 electron-builder 会触发
  隐式发布（上传 GitHub Release），本地没有 token 所以报错。该错误发生在
  产物已全部生成之后，不影响安装包；本地脚本已加 `--publish never` 禁用
  隐式发布（CI 走自己的 `--publish always`，见 §7）。

## 6. 常见问题

### 6.1 打包时 Electron 二进制下载失败

GitHub 直连问题，用镜像手动补：

```bash
ELECTRON_MIRROR="https://npmmirror.com/mirrors/electron/" node node_modules/electron/install.js
```

electron-builder 阶段同样加 `ELECTRON_MIRROR` 环境变量前缀。

### 6.2 「打开方式」里看不到 TMD

- 必须用**打包安装到 /Applications** 的版本（开发模式的 Electron 壳不会注册）
- 新装后等几秒或注销重登（LaunchServices 缓存），也可强制刷新：

```bash
/System/Library/Frameworks/CoreServices.framework/Frameworks/LaunchServices.framework/Support/lsregister -f /Applications/TMD.app
```

### 6.3 双击 .md 打开的还是旧版

打包后没有覆盖安装到 /Applications。执行 `npm run dist:install`。

### 6.4 包体积

当前约 **293MB**（2026-09-06 优化后）。构成：

- Electron 运行时（Chromium + Node + 框架）：约 250MB，**不可压缩**，Electron 应用的固定成本
- app.asar（应用代码）：约 6MB —— 所有依赖已由 vite 编译进 `dist/`，
  全部依赖放在 `devDependencies`，electron-builder 因此**不再打包 node_modules**
  （历史版本曾因生产依赖被打包而多达 489MB，mermaid 一个包就占 81MB）

注意：**新增依赖时一律加到 `devDependencies`**（`npm i -D`），否则 node_modules
会重新被塞进安装包。

### 6.5 自动更新

已接入 electron-updater，双源策略（Gitee 国内默认 + GitHub 备用）。
设置面板提供"启动时自动检查更新"开关与"检查更新"按钮。

- 发现新版本时弹窗问用户是否下载（不静默下载）
- Gitee 失败自动切 GitHub 重试一次
- macOS 未签名场景：关闭签名校验（自用）
- Gitee 源策略：元数据放仓库 raw 目录，大文件挂 Gitee Release 附件
  （详见 [§7](#7-ci-发布工作流) 的 Gitee 上传逻辑）
- Gitee raw 有 CDN 缓存（约 5 分钟），发布后稍等再检查


## 7. CI 发布工作流

配置文件：`.github/workflows/release.yml`，push tag `v*` 自动触发。

### 7.1 工作流设计

两个 job：

| Job | 平台 | 职责 |
|-----|------|------|
| `build` | macos-latest + windows-latest（并行） | 打包 + 上传 GitHub Release + 上传 artifact |
| `publish-gitee` | ubuntu-latest（依赖 build 完成） | 下载两平台 artifact + 上传 Gitee |

### 7.2 Gitee 上传逻辑

1. **元数据推仓库 raw 目录**：`latest*.yml` 通过 Gitee API 的
   `PUT /contents/releases/{name}` 更新（失败则 `POST` 创建）。
   这样 generic provider 的 `raw/master/releases/latest-mac.yml` URL 能访问到。
2. **大文件挂 Release 附件**：先 `POST /releases` 创建 Release，
   拿到 ID 后逐个 `POST /releases/{id}/attach_files` 上传 dmg/exe/blockmap。

> ⚠️ **Gitee 侧两条硬约束**（都踩过坑，改这块配置时务必注意）：
>
> 1. **分支名必须用 `master`**：Gitee 仓库默认分支是 `master`，不是 `main`。
>    内容 API 的 `branch`、Release 的 `target_commitish`、以及 package.json 里
>    generic 源的 raw URL 三处都要写 `master`。写成 `main` 时 API 直接失败，
>    元数据永远写不进仓库，Gitee 更新源会一直 404（只能回退到 GitHub 源）。
> 2. **附件单文件上限 100MB**：Gitee 免费版配额，超限文件被服务端拒绝。
>    Windows 安装包约 94MB 在限内；**macOS 的 dmg 约 116-124MB，必然超限**，
>    所以 Gitee Release 只能拿到 exe，dmg 请从 GitHub Release 下载。
>
> 上传失败一律让 job 失败（校验 HTTP 状态码后 `exit 1`），不再静默跳过。
> 因此**下一次带 dmg 的发布，`publish-gitee` 会变红**——这是预期行为
> （问题被暴露而非被吞掉），解决 dmg 分发方案后即恢复正常。

### 7.3 需要配置的 Secret

> ⚠️ 这是 CI 发布的**前置条件**，首次发布前必须配好。详见 [§3 前置条件](#3-正式发布触发-ci-自动打包--双源发布)。

| 仓库 | Secret | 用途 |
|------|--------|------|
| GitHub | `GITHUB_TOKEN`（自动提供） | 写 GitHub Release |
| GitHub | `GITEE_TOKEN`（手动配） | 调 Gitee API 上传产物 |

到 GitHub 仓库 `Settings → Secrets and variables → Actions → New repository secret`，
加 `GITEE_TOKEN`，值从 Gitee `设置 → 私人令牌` 生成（勾选 `projects`、
`issues`、`pull_requests` 权限）。

### 7.4 手动触发

GitHub Actions 页面可用 `workflow_dispatch` 手动触发，用于测试 CI 流程。
